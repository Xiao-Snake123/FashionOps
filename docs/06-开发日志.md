### 关键设计决策（面试可讲）

**决策一：路径沙箱用「解析后比较路径段」而不是字符串 `startswith`**

```python
# ❌ 错误做法：str(target).startswith(str(root))
#    /data-evil 会被误判为 /data 的子路径
# ✅ 正确做法：Path.relative_to() 会按路径段比较
def _is_relative_to(child, parent):
    try:
        child.relative_to(parent)
    except ValueError:
        return False
    return True
```

**决策二：给模型的错误必须带 `hint`**

`hint` 不是给人看的日志，而是**给模型的下一步动作建议**。
实测把 `hint` 加上后，模型面对 `file_not_found` 会先调 `list_files`，
而不是换个路径继续瞎试。

**决策三：产物统一落到 `outputs/` 且文件名必须清洗**

模型给的 `filename` 可能含 `../` 或 `/`。经 `safe_filename()` 清洗后
`../../evil.md` → `___evil.md`，再拼到 `outputs/` 下，双重保险。

### 设计要点

| 要点 | 说明 |
| --- | --- |
| **左闭右开** | 10:00–11:00 与 11:00–12:00 不算冲突，这是日历场景唯一合理的约定 |
| **相邻即合并 vs 相邻不冲突** | 看似矛盾，实则都对：合并是为了不生成 0 长度假空闲，严格比较是为了不误报冲突 |
| **时间统一带时区并转到配置时区** | 否则系统里会混着 `+00:00` 和 `+08:00`，排查时极易看错 |
| **导出 ICS 统一转 UTC** | 跨客户端兼容性最好的做法 |
| **查询用交集而非包含** | 08:00–20:00 的全天会议，查 12:00–13:00 也必须返回 |
| **明确不展开 RRULE** | 展开要处理 EXDATE/RDATE/时区/无限重复，属独立课题，当前明确不猜 |
| **忙碌情况可隐藏标题** | 跟外部方对时间时不该告诉对方"你在做什么" |

### 关键设计决策（面试可讲）

#### 1. 代码出数字和告警，模型只写解读

第一版把"严重程度"也交给模型判断，prompt 里明确写了「退货率 > 30% 才是 critical」。
**真实跑 glm-4-flash 时，它对 14.69% 的退货率照样标了 critical。**

这不是模型不听话，而是把不该它做的事派给了它。阈值判断是纯数值比较，
代码做得到 100% 准确且可复现。所以：

- 告警判定搬到 `agents/analytics_rules.py`（纯函数、可复现）
- 模型的 schema 里**直接删掉 `severity` 字段**，它就无从乱填

#### 2. 小样本不下结论

一个只有 3 单的类目退掉 1 单，退货率 33%，按阈值算是 critical。
但这是噪声。所以分组订单数 < 20 时**只报事实、不下判定**。

> 真实数据里最常见的坑不是漏报，而是把噪声当信号 —— 拿它去指挥业务，
> 就是"用统计学上无意义的数字做决策"。

#### 3. 邮件闸门：被拦的邮件也必须落库

`email_messages` 表的 `gate_decision` / `gate_reason` 一定写入，**不论放行还是被拦**。

如果只记"成功发出去的"，被拦的就完全不可见 —— 运维看到"这周只发了 12 封"，
却不知道还有 8 封被策略挡住、而业务方以为已经通知了。
**静默拦截比报错更危险，因为没人会去查。**

靠这个设计，界面可以直接做一个"被拦截邮件"列表，逐条讲得清**哪一层拦的、为什么拦的**。

#### 4. 被策略拦截 ≠ 节点失败

邮件被闸门拦下时，节点状态仍然是 `succeeded`，另外产出一个 `ApprovalRequest`。

因为从"节点执行"角度看它完成了工作（正确调工具、正确处理结果）；
从"业务"角度看需要**人工接手**。把它当异常会让上游重试 ——
而**重试一万次也不会让白名单多一条配置**。这是最典型的"重试解决不了的问题"。

#### 5. 能用代码可靠解决的，就不要交给模型

端到端跑通时发现 glm-4-flash 对「发给 ops@example.com」这种
**明确写在需求里**的地址都没稳定提取出来。所以加了正则兜底，
并在 findings 里记录 `recipient_source`（`caller` / `model` / `regex_fallback`）。

邮箱是完全规则的东西，正则能 100% 提对；让它去靠模型的"理解"属于自找不确定性。

### 踩坑记录

#### ① MySQL 8.0 不支持 `ORDER BY x NULLS LAST`

切库当天 `/api/v1/campaigns` 直接 500：

```
pymysql.err.ProgrammingError: (1064, "...near 'NULLS LAST) AS anon_1'")
```

排序写的是 `AdCampaign.roi.asc().nulls_last()`。SQLite 3.30+ 支持这个语法，
**MySQL 8.0 不支持**（MariaDB 才支持）。改用不依赖方言的写法：

```python
null_rank = case((AdCampaign.roi.is_(None), 1), else_=0)
stmt = stmt.order_by(null_rank, AdCampaign.roi.asc())
```

**为什么单元测试没拦住**：测试跑 SQLite、开发库也是 SQLite ——
**测试和开发同源，就永远测不出方言差异**。新增 `tests/test_api_mysql.py`（19 项）
拿真 MySQL 打遍全部只读接口，连不上自动跳过（沿用 `test_gateway_redis.py` 的模式）。

已反向验证测试有牙齿：把 `nulls_last()` 改回去，用例立刻红且报错一字不差。

顺带自查通过的方言点：`func.date()` 分组、`case()` 条件聚合、outer join、`count(distinct)`。

#### ② 中文文件名不能直接当对象存储 key

存储 key 必须 ASCII 安全（要进 URL、HTTP 头、对象存储规范），
中文直接当 key 会触发 `PathEscapeError`。而且只靠"日期 + 文件名"不保证唯一 ——
同一天两份「经营分析.xlsx」会互相覆盖，`assets` 表却留两条记录指向同一个文件。

拆成两个字段：`assets.name` 保留人类可读的中文名；存储 key 收敛成 ASCII
并拼一个 `uuid4().hex[:8]`。

#### ③ 模型的空收件人只会在网关报一个看不懂的错

节点把空收件人传给 `mail.send`，网关回 `[INVALID_ARGUMENTS] 参数校验失败：1 处不合法` ——
看不出是哪个参数、更看不出"其实是你没给收件人"。

**这类"能跑但报错信息没用"的失败是真实事故排查里最耗时的一种。**
所以在节点里提前拦下来，并把已写好的草稿放进审批请求 ——
人补一个地址就能发，不用从头再来。

#### ④ 测试造的外部状态必须自己能收干净（老坑复发）

邮件闸门默认用 Redis 限流器，键是全局的 `mail:<地址>`。
于是同一个地址跨用例累计计数，第二个用例就莫名被 `blocked_ratelimit` 挡住。

修法是测试里把限流器换成进程内的 `MemoryRateLimiter`。
这条坑仓库里已经记过一次（`test_gateway_redis.py`），这次是复发 ——
**凡是测试触碰到"进程外状态"，都必须显式隔离。**

#### ⑤ `args_model=None` 网关处理不了

注册 `mail.policy` 时想表达"无参数"就传了 `None`，结果网关去调
`args_model.model_json_schema()` 直接 `TypeError`。改用空 Pydantic 模型 ——
既表达"无参数"，又让暴露给模型的 schema 是个合法的空对象。

### 关键设计决策（面试可讲）

#### 1. 模型出计划，代码校验计划

让模型自由生成执行计划很有吸引力，但它会**稳定地产出跑不通的计划**，而且是静默的：
编出不存在的 Agent、`depends_on` 指向不存在的 step_id、步骤成环、
同一个 Agent 出现两次（图是静态构建的，一个 Agent 一个节点，路由分不清第几次）。

所以是两道关：Pydantic 管结构，`validate_plan` 管语义，不过就**带着具体问题回喂重试**，
还不过就回退到代码生成的默认计划。**规划是优化项，不是关键路径** ——
做成关键路径等于每次任务都有概率因为一句没写好而全盘失败。

#### 2. `agent` 做成 `Literal`，约束进 schema

比"生成完再校验然后回喂重试"少一轮往返，`mock` 生成器也能自动产出合法值。
`validate_plan` 里的 `unknown_agent` 检查保留，兜从 checkpoint 读回的外部计划。

#### 3. hub 条件路由，执行顺序完全由计划决定

写死 `plan → selection → analytics → notification` 简单得多，但那样"计划"就只是个装饰品。
用 hub 路由后，用户只说"出份报表"，图上就只跑 analytics 一步，不白跑选品。

#### 4. 上游失败必须阻断下游（传递阻断）

`blocked_steps` 算的是**传递闭包**，不是只看直接依赖。
原因：A 失败 → B 依赖 A → C 依赖 B。只看直接依赖的话 C 被认为"可以跑"
（它的依赖 B 既没成功也没失败），于是 C 带着空输入跑出一个看起来正常的结果 ——
**这比直接失败危险得多，因为它会被人当真。**

#### 5. 记录是旁路，不是主路

`TaskRecorder` 所有写入都是尽力而为，失败只告警不抛异常。理由：写库失败不该让业务失败。
但代价是**它会掩盖自己的 bug**（见下文①）。

### 踩坑记录

#### ① 记录器让"批准之后的事件全丢了"（最严重的一个）

批准任务后 `task_events` 里只有批准前的 9 条，之后的全部不见了。

根因：`build_runner` 每次都会**新建** `TaskRecorder`，它的 `_seq_cache` 是空的 ——
resume 时 seq 从 1 重新开始，撞上 `uq_task_event_seq` 唯一约束，插入失败被 `_safe` 吞掉，
日志里只有一行 warning。

修法：`event()` 首次用到某个任务时**从库里取 seq 基线**。
另外加了 `write_failures` 计数器 —— 让"记录被静默丢弃"变成**可断言**的事实。

> 这个 bug 特别值得记：它是"记录失败不影响业务"这个设计**自己掩盖**的。
> 如果没有那条容错，插入失败会直接报错，一眼就能看到。

#### ② 审批闸口拿 `route` 当 step_id → 无限弹同一个审批

`route` 在等审批时是哨兵值 `__approval__`（条件边只能读那个），
拿它当 step_id 会把批准结果记到哨兵头上，hub 下次还判"这一步没批"。

修法：新增 `pending_step` 字段专门存真实 step_id。
教训：**一个字段不要同时承担"路由信号"和"业务标识"两个职责。**

#### ③ 通知 Agent 硬依赖 `findings['analytics']`，模型漏拆一步就整条挂

真实现象：用户说"选 2 款女装并出报表发给 ops@x.com"，模型把「选品 + 分析」
合并成一个步骤（`agent` 只写了 selection），于是 analytics 没跑，
通知节点因为拿不到 `findings['analytics']` 直接失败。

修法两层：
- **通知节点与上游解耦** —— 它的职责是"把已有结论组织成邮件"，不是"等某个特定上游"。
  只要有 selection 或 analytics 任意一条结论文，它就应该能干活
- **规划校验补一条确定性规则** —— 用户需求里点名要的能力（按关键词识别）
  不能在计划里缺席，漏了就回喂让模型重拆

#### ④ mock 生成器把字段的 `description` 当值用

原意是"作者写给人看的解释，当样本很合适"，但实际产出的是
`"执行该步骤的 Agent，必须从给定列表里选"` 这种句子，永远不可能是合法值。
**`description` 是文档，不是例子。**

顺带修了第二个问题：`step_id` 命中了提示表里的
`("stage", "step", "phase") → "analyze"`，于是列表里每个元素都叫 `analyze` ——
生成出来的计划必然报 "step_id 重复"，而 mock 的本意是生成**合法**数据。

修法：先按提示表拿到可读样本，再给标识符类字段接一个唯一后缀
（`SKU00001_483920`）。两边诉求都照顾到，后缀用下划线以兼容 `^[a-z][a-z0-9_]*$`。

#### ⑤ `langgraph-checkpoint-redis` 需要 RedisSearch，普通 Redis 用不了

启动时报 `unknown command 'FT.INFO'` —— 这个包依赖 Redis Stack 的 RediSearch 模块，
而本机是 msys2 的 portable Redis，没有该模块。好在
`checkpoint.py` 的降级路径生效了，自动退回 SQLite（单进程可恢复）。

**不影响功能**：Redis 仍然在给限流计数用（那是普通的 `ZADD`/`ZCARD`）。
但需要在文档里说清楚，否则会被误认为"checkpoint 进了 Redis"。

#### ⑥ 测试里查状态用了不同 backend 的 checkpointer

`get_checkpointer()` 不带参数会用**真实应用配置**（可能是 Redis），
而图是用内存 checkpointer 跑的 —— 拿到的是另一个实例，
表现为"查不到状态"，看起来像图没跑。测试里必须把 saver 一并返回、复用同一个实例。

### 关键设计决策（面试可讲）

#### 1. 归一化放在**唯一出口**，不是放在一个路由里

库里存着两种 DAG 形状（seed 的 `{nodes, edges}` 和 W4 起的 `{steps}`）。
W4 时我在 `get_task` 里手动调 `normalize_dag` —— 结果是**列表和详情返回两种形状**，
前端每处渲染都得写 `if` 分支。

改法：`normalize_dag` 搬到 `agents/planner.py`（它拥有 `PlannedStep`/`TaskPlan`，
是形状的权威），然后在 `api/schemas.py` 的 `TaskOut` 上挂 `@field_validator(mode="before")`。
**所有出口自动生效**，以后再加接口也不用记得调。

#### 2. SSE 帧不写 `event:` 名，类型只存一份

一开始按 SSE 惯例发了 `event: <event_type>`。问题：事件类型已经在 `data.event_type` 里了，
再在 `event` 字段写一遍就是**同一份信息存两处** ——
代价是前端得为每个类型各注册一个监听器，于是后端新增一种事件时前端**静默漏掉**
（不报错，只是不显示）。

改成只发 `id:` + `data:`，全部落到 `EventSource.onmessage`，一个 handler 接住任意类型。
控制帧（`done` / `task_error`）用 `data.type` 判别。

顺带修了一个命名冲突：控制帧原来叫 `error`，而 `EventSource` **自带** `error` 事件
（网络断了、连接被掐）。同名的话一个 handler 会被两种完全不同的情况触发，
只能靠 `'data' in event` 猜来源。

#### 3. 审批做成常驻横幅，不是弹窗

弹窗能被随手关掉，而"任务卡在等你点确认"这件事关掉后就没地方看了。
横幅上**必须**显示两个字段，否则用户只能盲批：

- `action`：要干什么（模型写的人话，如「执行「将经营分析报表发送给 ops@example.com」（notification）」）
- `reason`：为什么要人点（「步骤 send_report 被标记为需要人工确认。它会产生对外不可撤销的副作用」）

第一版只显示了 `agent` / `step_id`，等于让用户对着"由 notification 在 send_report 触发"做决策。

#### 4. 界面上的四个状态要分开说，不能只看"字段有没有值"

一个任务可能：整体成功但邮件被拦、或被人主动驳回。
这两种情况下 `error_message` **都有值**（这是有意保留的信息），
但第一版一律显示成红框「失败原因」—— 用户看到一个绿色「成功」badge 配一个红框「失败原因」。

改法：按终态挑措辞。

| 终态 | 显示 |
| --- | --- |
| `failed` | 红框「任务失败」 |
| `cancelled` | 黄框「任务已被人工取消」 |
| 其余 | 黄框「任务已完成，但有需要留意的地方」 |

同理，人工取消原来复用了 `task_failed` 事件名 —— 读事件流的人会去查错误栈，
而取消根本没有错误。新加了 `EVENT_CANCELLED = "task_cancelled"`（level `warn`）。

### 踩坑记录

#### ① `POST /tasks` 返回的 task_no 立刻查是 404 → 详情页永久卡死（最严重）

界面上点「提交任务」→ 自动跳到 `/tasks/T26091207...` → **「请求失败：404 Not Found」**。
任务确实存在（`created_at` 比浏览器那两次请求晚 2 秒）。

根因：`submit_task` 把活丢给线程池就 `return`，`tasks` 行是**后台线程**插的 ——
接口返回时那个 id 还查不到。

为什么危害比看起来大：首次加载失败导致 `task` 是 `null`，
于是 **SSE 也不会挂上**（挂载条件是 `task !== null && is_pending`）——
等任务真跑起来后页面**永远不会自己恢复**。

修法：新增 `_create_task_row()`，**先落库再返回**，状态给 `pending`
（`pending` 也在 `_RUNNING_STATES` 里，前端照样会挂 SSE 等它）。

> 为什么手工测不出来：**人打完一条 curl 再敲第二条，中间隔着好几秒，
> 刚好够后台线程把行写进去。**只有真实客户端才会在毫秒内发第二次请求。
> 教训：凡是"提交返回一个 id、客户端拿它查详情"的接口，返回前必须保证 id 可查。

#### ② REST 和 SSE 把同一个事件对象发成了两种形状

`/events` 返回 `node` / `agent` / `occurred_at`，SSE 返回 `node_name` / `agent_name` / `created_at`。
前端要写两套解析，改一处必漏另一处。

修法：`read_events()` 统一按 `TaskEventOut` 的字段名输出，`get_events` 直接复用它 ——
**两条路走同一份实现**。顺带发现 `total_cost` 也是不一致的（详情是 `float`、列表是 `Decimal`），
统一成 `TaskDetailOut` schema 后由 Pydantic 决定序列化。

#### ③ 路由重复定义 → FastAPI 静默取先注册的

`business.py` 里被插入过两次 `/emails` 和 `/emails/stats`。不是报错，而是"改了代码没生效"。
ruff 的 `F811 Redefinition of unused list_emails` 先报了出来。

删的时候 `@router.get("/kb")` 这个锚点不存在（路由顺序和我以为的不一样），
改用行号切片才成功。

#### ④ 把 `normalize_dag` 搬走之后，`tasks.py` 里残留调用 → `F821 Undefined name`

ruff 的 `--fix` 会自动清理**未使用**的导入，但不会发现"引用了已搬走的名字"。
只报在一个地方，跑一次 `ruff check src` 就抓到了。
**这说明每次批量编辑后立刻跑 lint 是必需步骤，不是可选项。**

#### ⑤ 前端 `<>` 简写片段不能带 key

Emails 页每个列表项是"主行 + 展开行"，用 `<>` 包起来时 key 只能写在里面的 `<tr>` 上，
React 会报列表 key 缺失。要用 `<Fragment key={...}>`。

#### ⑥ 前端 eslint 没装（仓库里也没配置）

`npx eslint src` 会触发联网安装 eslint 10，然后卡在 `Ok to proceed? (y)`。
**这个项目没有 eslint 配置**，验证前端就是 `npm run build`（= `tsc --noEmit && vite build`）。

#### ⑦ Vite 端口被旧实例占着

`npm run dev` 报 `Port 5173 is in use, trying another one...` → 实际跑在 5174。
**别假定端口**，先看 `data/logs/web.out.log` 里打的那一行。

顺带：`npm` 是 `.cmd`，`Start-Process -FilePath "npm"` 起不来，
要 `Start-Process cmd.exe -ArgumentList "/c npm run dev > ..\data\logs\web.out.log 2>&1"`。

#### ⑧ 页面快照会早于异步数据到达

用浏览器工具读页面时，第一次快照经常显示"加载中…"或"共 0 条"，
但接口其实是好的（直接 `curl` 能拿到 25 条）。**等一下再看**，不要据此改代码。

### 关键设计决策（面试可讲）

**1. 权限码写在代码里，角色写在数据里。**
新增一个权限是**代码变更**（要同时改工具声明），新增一个角色是**数据操作**。
把权限码也做成可增删的数据，等于让"某次运维操作"就能扩大系统权限边界 —— 这是安全和审计上的大忌。

**2. 审计字段存 username 快照，不只用外键。**
`tasks.created_by_id` 是外键（`ON DELETE SET NULL`），但旁边还存 `created_by`（字符串快照）。
理由：用户被删号之后，**"当时是谁批的"必须有答案**。外键被置空会让责任链断掉，
而审计的第一价值就是"事后能追责"。

**3. refresh token 在库里存哈希，不存明文。**
企业场景需要"立刻踢下线"（离职、手机丢失），所以必须服务端可控 → 必须落库。
但落库的是哈希：数据库被读走也换不出可用 token。**"能撤销"和"不存明文"不冲突。**

**4. `password_hash` 可为空。**
钉钉/企业微信扫码登录的用户没有密码。设计时就把这个留出来，
而不是等接入 SSO 时再改表。

**5. `check_config()` 必须用 `type(settings).model_config`。**
写成 `Settings.model_config` 的话会**忽略调用方传进来的 `env_file`** ——
结果是这个函数在测试里根本没法跑（读到的是真实 `.env`）。
这是"看起来等价、实际不等价"的一类 bug，靠测试发现。

**6. `extra="ignore"` 保留不改 `forbid`。**
`forbid` 会让一个拼错的变量名**直接启动失败**，听起来更"安全"。
但真实后果是：用户在 `.env` 里多写一行注释性变量，服务就起不来了 ——
这是把"发现问题"变成"制造故障"。正确做法是**允许启动但主动报告**，
所以有了 `fashionops-config check`（见下面的真 bug）。

**7. `request_context()` 退出时必须清理 contextvar。**
线程池会复用线程，不清理的话上一个请求的 `request_id` 会粘到下一个请求的日志上 ——
排查时会把两个不相干的问题串成一条线，比没有 request_id 更糟。

**8. 日志流强制 UTF-8。**
Windows 的 stderr 默认是 GBK。不处理的话不只是日志文件变 GBK，
更糟的是：**含不可编码字符的日志记录会被 logging 静默丢弃** ——
中文错误信息越多，丢得越多，而日志库不会告诉你。

### 踩坑记录

#### ① `alembic.ini` 里有中文 → **每一条 alembic 命令都失败**

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xe6 in position 42
```

Alembic 用 `encoding="locale"` 读 ini 文件，`PYTHONUTF8=1` **不起作用**
（它在读 ini 之前就决定了编码）。

修法：`alembic.ini` 保持纯 ASCII，中文注释全部挪到 `env.py` 和文档里。
并且 `fashionops-db` 命令改用**程序化构造 `Config()`**，这样即使 ini 坏了也有救急通路。
补了 2 个测试把这个约束锁住 —— **这条约束不写测试，下次改配置的人一定会踩。**

#### ② Alembic 自动生成的匿名外键 → downgrade 跑不了

`create_foreign_key(None, ...)` 生成的外键在 MySQL 上名字是自动生成的，
`downgrade` 里想 `drop_constraint` 却不知道该删哪个名字。
Alembic 自己也会警告 "this directive will fail as rendered"。

修法：所有外键**显式命名**（`fk_tasks_created_by_id_users` 这种），downgrade 按名字删。

#### ③ `drop_index` 在 `drop_table` 之前 → MySQL 报 errno 1553，**SQLite 上完全看不出来**

MySQL 的外键会**复用同名索引**。先 `drop_index` 会把外键依赖的索引干掉，于是报 1553。
而 `DROP TABLE` 本来就会连带删掉这些索引 —— 那 23 个 `drop_index` 块是**多余的**。

修法：删掉 23 个冗余块，并加了一个**静态检查**（`_find_redundant_index_drops`）
+ 一个专门验证这个检查器**有牙齿**的测试。
**教训：只删代码不加检查，"下次又写回来"是必然的。**

#### ④ MySQL 的 DDL 不是事务性的 → 迁移失败会留下半完成状态

SQLite 的 DDL 在事务里，失败会整体回滚，所以本地测不出问题。
MySQL 上 "CREATE TABLE 成功 + 后面某步失败" 会让库停在**不一致状态**，
而 `alembic_version` 还停在旧版本 —— 重跑会从第一步开始，直接撞上"表已存在"。

这条没有代码解法，只能写成铁律：**大 DDL 前先备份**；
用 `alembic upgrade head --sql` 先看要执行什么；用 `alembic check` 检测漂移。

#### ⑤ 真 bug：用户 `.env` 里写了一个**不存在的**变量名，被静默忽略

用户配的是 `FASHIONOPS_MAIL_SMTP_HOST`，而真实字段名是 `FASHIONOPS_SMTP_HOST`。
`extra="ignore"` 让它**完全不报错**，服务照常启动，
只是发信时连不上 SMTP —— 而错误信息里看不出是"变量名写错了"。

同一个 `.env` 里 `SMTP_HOST` 的值填的是**一个邮箱地址**而不是 `smtp.qq.com`。

修法：`config_doctor.py` 从 `Settings.model_fields` **反推**所有合法键名
（不是手写列表 —— 手写的列表会随字段增删过期），
未知键、拼写近似（`difflib`）都报出来并给建议。

#### ⑥ 全项目**从来没配置过 logging**

所有 `logging.getLogger("fashionops.x").info(...)` 调用都进了黑洞：
根 logger 默认是 WARNING，而代码里没有任何地方 `basicConfig` / `dictConfig` / `addHandler`。

**这个问题的可怕之处在于它完全不报错。** 服务跑得好好的，
只是"为什么这里没日志"永远没人回答得了。

修法：`logging_setup.py`。关键是 `ProcessorFormatter`：
structlog 接管渲染，但**已有的 stdlib logger 调用一行都不用改**。
否则就是"为了加日志而改 20 个文件"，改的过程中必然出错。

#### ⑦ 屏蔽列表里有 `httpx`，噪音却还在

`openai` 这个 SDK **把 httpx 内嵌成了一个副本**，logger 名字是 `httpx2` / `httpcore2`。
硬编码名字列表抓不到。

修法：把"名字列表"换成**前缀匹配的 handler filter**。
好处是**之后新建的 logger 也自动被覆盖** —— 名字列表永远有漏的。

#### ⑧ `.env` 改了必须重启 API 进程

配置是 `lru_cache` 单例，热更新不存在。这条要写进运维手册，不能靠记忆。

### 关键设计决策（面试可讲）

**1. 不用 Milvus 的理由是"架构不匹配"，不是"不够好"。**
Milvus 最小部署就要 etcd + MinIO（它是计算层，自己不落盘数据）——
在 17 条向量上引入两个分布式组件，**它们挂掉时 RAG 整个不可用，
而这两件事和检索质量毫无关系**。完整对比见 `docs/10` §1。

**2. `VectorStore` 抽象的三个**具体**理由（不是"便于移植"）：**
① 单元测试不能依赖外部服务（否则 CI 要装 Qdrant，"要装东西的测试"最终没人跑）；
② "测试过 ≠ 生产能用"需要用真组件验证 —— 所以有双后端契约测试；
③ 切分/BM25/RRF/重排与存储无关，只该依赖接口。

**3. 抽象层刻意**薄**：不做 ORM 式文档模型。**
Qdrant 的 payload 过滤会**下推到 HNSW 遍历内部**（走图时就跳过不匹配的点），
这是它相对 pgvector 的核心优势。把 payload 包进领域模型会吃掉这个能力，
退化成"先取 top-k 再过滤" —— 过滤条件一严结果就空。
**抽象层的厚度必须小于它包住的能力。**

**4. 索引故障 ≠ 没搜到。**
`search_kb` 在 collection 不存在/为空时**抛 RuntimeError**，而不是返回 `[]`。
工具层翻译成两个 `reason`：`index_not_ready`（运维问题）vs `no_match`（业务结论）。
混为一谈的后果是：客服对用户说"知识库里没有这个问题的答案"，
而真实原因是运维忘了建索引 —— **用户拿到一个假结论，且它听起来像真的。**

**5. 不做向量库自动降级（和限流器相反）。**
限流器降级 = "这次没拦住"，可控；向量库降级 = **索引是空的**，
Agent 会把"空"当事实告诉用户。**静默变空比报错危险得多。**

**6. 离线向量化必须是"真的按字面重合给分"的哈希向量，不能是随机数。**
随机向量也能让"维度对不对、写完读得到吗"通过，但**检索质量完全测不了** ——
断言只能退化成"返回了 3 条"。用符号散列之后，
离线也能写 `assert search_kb("退货怎么处理")[0]["article_no"] == "KB-0001"`。

**7. 换 embedding 模型必须报错，不能自动重建。**
两个模型的向量空间不兼容，混用会产生**看似正常但实际无意义**的相似度 ——
比直接报错危险得多。但也不该"自动"重建：自动重建是**破坏性操作**，
用户只是改了个环境变量想试试，结果索引被清空了。**破坏性动作必须显式。**

**8. `retrieval_text` 与 `content` 分开。**
正文里"亲，感谢您的支持"这类句子会把向量往"客服用语"方向带偏，
**压平所有文章之间的相似度差异**。所以专门有一个只喂 embedding 的字段。

### 踩坑记录

#### ① 契约测试第一次运行就抓到真 bug：Qdrant 返回的是存储层 UUID

| 后端 | 返回的 `VectorHit.id` |
| --- | --- |
| memory | `"near"`（调用方传什么就返回什么） |
| **qdrant** | `"6fa7f901-802c-58e9-..."` ← **UUID** |

Qdrant 的 point id **只接受整数或 UUID**，适配器把 `"kb-0001#3"` 映射成了 `uuid5`，
但第一版**直接把存储层 id 返回了**。

为什么危险：调用方拿到的 id **无法反推来源**（排查时答不上来"这个向量是哪篇文章的"），
而且**两个后端行为不一致** —— **只跑一个后端完全看不出来**。

修法：写入时把逻辑 id 一并写进 payload（`PAYLOAD_ID = "_id"`），检索时原样还回去并 pop 掉。
**存储层怎么编码 id 是实现细节，不该泄漏到接口上。**

#### ② 距离度量方向相反

欧氏/曼哈顿是**越小越相似**，余弦/内积是**越大越相似**。
不归一化的话，`search()` 的调用方得知道底层用的哪种距离，
"过滤后按 score 排序"这类通用逻辑就写不出来。

修法：`_normalize_score()` 对 euclid/manhattan 返回 `1/(1+d)`，**统一成"越大越相似"**。

#### ③ 189 秒的测试文件 = 没人跑的测试文件

`delete(collection)` 原本实现成"删掉 collection 再重建"，更"干净"，
但每用例重建要重新为 4 个字段建 payload 索引（每个都是带 `wait=True` 的往返），
于是 23 个用例 × 4 个索引 = 76 次阻塞往返 → **189 秒**。

改成「**只删点、保留 collection**」后降到 **8 秒**（23 倍），而且**语义更对**：
清空数据不该顺带把维度/索引这些**配置**扔掉。另补独立的 `drop_collection()`
给"换模型导致维度变了"的场景（那时 `size` 已固定，只能拆掉重建）。

> 顺带的经验：**慢测试的下场是被临时跳过，然后渐渐没人记得它测什么。**

#### ④ 切分的一个真缺陷：短路判断用错了阈值

```python
if len(text) <= MAX_CHUNK_CHARS:   # ← 900，错
    return [text]
```

后果：一篇 **700 字、讲了尺码+退货+物流三件事**的文章，因为没超过 900
被整篇返回成**一个** chunk，向量被三个主题平均化 ——
**正好是本模块开头说要避免的情况**。应该比 `target_chars`（400）。

`MAX_CHUNK_CHARS` 是**不可逾越的硬上限**，`target_chars` 才是**目标粒度**。

#### ⑤ 测试数据自己太短，把 bug 藏起来了

写这个测试时第一版长文档只有 720 字（6 段 × 120 字），
**根本没触发多块路径**，所以上面那个缺陷没暴露。
改成 6 段 × 280 字（约 1700 字）才抓到。

> **教训：验证"边界处理"的测试数据必须真的越过边界，不能"看起来很长"。**

#### ⑥ PowerShell 的编码有三个独立开关

`chcp`、`[Console]::OutputEncoding`、`PYTHONIOENCODING` 各管一段，
任缺一个就出乱码。而本项目里 **Python 的 stderr 被 `logging_setup` 强制成 UTF-8**，
stdout 却跟控制台代码页 —— 于是同一条命令的**日志和 print 输出编码不同**。
排查时直接写文件再读，别在终端里较劲。

#### ⑦ 改完 `.env` / 代码后：必须重启 API 进程

配置是 `lru_cache` 单例。这条已经踩过第二次了，写进运维手册。
