### 关键设计决策（面试可讲）

**决策一：路径沙箱用「解析后比较路径段」而不是字符串 `startswith`**

```python
# ❌ 错误做法：str(target).startswith(str(root))
#    /data-evil 会被误判为 /data 的子路径
# ✅ 正确做法：Path.relative_to() 会按路径段比较
def _is_relative_to(child, parent):
    try:
        child.relative_to(parent)
    except ValueError:
        return False
    return True
```

**决策二：给模型的错误必须带 `hint`**

`hint` 不是给人看的日志，而是**给模型的下一步动作建议**。
实测把 `hint` 加上后，模型面对 `file_not_found` 会先调 `list_files`，
而不是换个路径继续瞎试。

**决策三：产物统一落到 `outputs/` 且文件名必须清洗**

模型给的 `filename` 可能含 `../` 或 `/`。经 `safe_filename()` 清洗后
`../../evil.md` → `___evil.md`，再拼到 `outputs/` 下，双重保险。

### 四层发送闸门的设计

| 层 | 规则 | 理由 |
| --- | --- | --- |
| 1 | **白名单为空 → 禁止发送** | fail-closed：漏配的后果应该是「发不出去」而不是「能发给任何人」 |
| 2 | 黑名单优先 | 给管理员一个紧急刹车 |
| 3 | 收件人数 + 附件扩展名 + 附件大小 | 挡群发、挡 `.env`/私钥外发 |
| 4 | 滑动窗口限流 | 挡模型循环发信 |

配套两条：

- **`to`/`cc`/`bcc` 全部校验** —— 只看 `to` 的话，把目标塞进 `cc` 就绕过了。
- **被拒时 `hint` 指向 `save_email_draft`** —— 让 Agent 有路可走，而不是卡死或反复重试。

### 踩坑记录

| # | 问题 | 原因 | 解决 |
| --- | --- | --- | --- |
| 8 | **BCC 收件人根本收不到邮件** ⭐ | `_build_message` 只设了 `To`/`Cc`，漏了 `Bcc` 头。`smtplib.send_message` 是从 `To`/`Cc`/`Bcc` 汇总收件人的 | 补上 `message["Bcc"]`。测试 `test_cc_and_bcc_included_in_message` 守住 |
| 9 | 附件策略检查抛 `AttributeError` | `_collect_attachments` 返回 `list[dict]`，闸门期待 `AttachmentInfo` | 引入 `ResolvedAttachment` 数据类，把"已校验的元信息"和"实际路径"绑在一起，避免"检查的是 A、发出去的是 B" |
| 10 | 草稿文件名含 `..` | `client.py` 里另写了一份文件名清洗，漏了 `..` 折叠 | 改为复用 `common.paths.safe_filename`，消除重复实现 |
| 11 | **`dry_run` 模式下限流完全失效** ⭐ | `record_sent()` 在 `dry_run` 的 `return` 之后才调用 | 改成 `record_attempt()` 并在分支**之前**记账。理由：dry_run 的价值就是离线跑通整条策略链路，跳过限流等于上线才第一次触发 |
| 12 | 测试报 `Settings() got multiple values` | fixture 默认参数与 `**overrides` 重复 | 改用 `options.update(overrides)` |

> 8 和 11 都是**真实功能性 bug**，且都属于"不写测试/不做端到端演示根本发现不了"的类型：
> BCC 漏设 = 密送功能完全不可用；dry_run 跳过限流 = 限流策略从未被验证过。
