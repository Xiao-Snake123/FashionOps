# 优化了什么，为什么这么优化

> 这份文档回答两个问题：**改了什么**、**为什么这么改**。
> 按优先级从高到低排列，每条都写清「原来的问题 → 为什么它是瓶颈 → 怎么改的 → 取舍依据」。
> 待办清单与遗留项见同目录的 `优化.md`；本文与之配套，但侧重于**决策理由**。
>
> 实施完成时间：2026-09-20。验证：全量测试 574 passed，`ruff` 源码全通过，前端 `tsc --noEmit` 通过。

---

## 总览

| # | 优化项 | 解决的核心问题 |
|---|---|---|
| 1 | 启用 Redis 业务缓存 | 首页/报表类接口每次请求都跑一遍聚合 SQL |
| 2 | 会话历史改为按需加载 | 长会话每打开一次、每回合结束都全量拉历史和工具 JSON |
| 3 | 前端接收工具消息、去掉全量重拉 | 同上（这一条是第 2 条能成立的前提） |
| 4 | Agent 链路去冗余查询 | 任务执行过程中反复查同一批数据 |
| 5 | 补齐分页与真实 `total` | 有的接口全表返回；有的 `total` 是错的 |
| 6 | 补两个索引 | 过滤 + 排序没有可用索引，触发 filesort |
| 7 | 前端渲染与分页 | 无谓重算；第 51 个会话永远看不到 |
| 8 | 理顺 Redis 库用途 | db1 闲置、网关占了 db2，职责混乱 |

贯穿全局的一条设计原则：**缓存/加速器永远不能成为依赖**。以下所有涉及 Redis 的改动，
在 Redis 挂掉时都会静默退化为"不用缓存"，接口照常返回正确结果。

---

## 1. 启用 Redis 业务缓存（P0，收益最大）

### 原来的问题
`cache.py` 的注释里把 Redis 的 **db2 定义成"业务缓存：列表页、聚合结果"**，
但翻遍代码只有网关的幂等存储用它，**没有任何一个读接口命中它**。
也就是说：db2 常年空转，而首页、报表、选品这些接口每次都直连数据库重新聚合。

受影响最典型的是 `/api/v1/summary`：一次请求要跑十几条聚合 SQL，
还包含一个 `Inventory` 的 `GROUP BY` 子查询加 JOIN。而这些数据是分钟级变化的。

### 怎么改的
- `cache.py` 新增四个函数：`business_cache_key` / `read_cached_json` /
  `write_cached_json` / `invalidate_namespace`。
- `config.py` 新增 `business_cache_enabled`（总开关）和 `business_cache_ttl`（默认 30 秒）。
- 接入 5 个接口：`summary`、`metrics/daily`、`products/categories`、`inventory/low-stock`、`kb`。

### 为什么这么改
- **为什么是查缓存而不是改 SQL**：这些聚合本身已经写得没什么优化空间了，
  真正的问题是"同样的结果被算了无数次"。加缓存是直接针对病根的改法，且改动面最小。
- **为什么失效用"版本号"而不是逐个删 key**：`invalidate_namespace` 只把一个计数器 +1，
  之后拼出来的 key 自然落在新版本上，旧 key 等 TTL 自动消失。
  比"找出所有相关 key 再 DEL"可靠得多 —— 后者一旦漏拼一个前缀就是永久脏数据。
- **为什么 key 里必须带上所有查询参数**：比如 `low-stock` 的 `threshold`。
  漏了的话，用 `threshold=5` 查一次之后，`threshold=50` 的请求会拿到 5 的结果。
- **为什么要能整体关掉**：见下面「踩过的坑」。

### 主动失效
光有 30 秒 TTL 不够直观：用户刚点了"批准"，回头看到"运行中 0"会很困惑。
所以把失效接进了 `agents/recorder.py` 的状态变更点（`start` / `update_progress` / `finish`），
任务状态一变就让 `summary` 失效，而不是干等 TTL。

### 踩过的坑（重要）
**测试里必须关掉缓存**，否则会跨用例串数据：每个测试用例用的是**自己那份临时 SQLite 库**，
而 Redis 是**全局共享**的一份。用例 A 缓存的结果会被用例 B 读到。
更麻烦的是这类失败只在 Redis 真的在跑时才复现 —— 本地没起 Redis 反而"一切正常"。
所以 `tests/conftest.py` 里加了 autouse 夹具 `business_cache_off` 强制关闭。

## 2. 会话历史改为按需加载（P1）

### 原来的问题
`GET /api/v1/conversations/{no}` 是**不限量返回全部历史消息**。
一场聊了 200 句的会话，每次打开详情都要把几百行消息拉出来 ——
而每条工具消息里可能带着几千字的返回 JSON，恰恰是最重的部分。
限制 context 本来是为了省下这笔开销，结果全量拉取等于白省（原 `store.history` 注释里也写了这点）。

### 怎么改的
- 后端：默认只回最近 **100** 条（`DEFAULT_HISTORY_LIMIT`），上限 500，
  新增 `?before_seq=` 用于向上翻页，响应新增 `has_more`。
- `store.history()` 增加 `before_seq` 上界，仍然走倒序取末 N 条再翻转的写法，
  继续复用 `ix_chat_msg_conv_seq` 定位末尾。

### 为什么这么改
- **为什么默认 100 而不是 20**：这是"打开详情"的首屏，100 条足够覆盖正常阅读范围，
  20 条会让用户一进来就看到"加载更多"。
- **为什么 `has_more` 靠"多取一条"判断，而不是 `COUNT(*)`**：
  反正已经用索引定位到末尾了，多取一条几乎不花钱；`COUNT(*)` 是额外一次全量扫描。
  （不这么做的话，前端只能拿"返回条数 == limit"去猜，恰好整除时会误判成"没了"。）
- **为什么保留 `limit` 可配置**：给将来"想一次多拿点"的调用方留空间。

## 3. 前端接收工具消息、去掉每回合全量重拉（P1）

### 原来的问题
前端每次发完消息，都会在 `finally` 里**再拉一遍整个会话详情**，
名义是"刷新标题/计数/成本"，实际是补救一个 bug。

### 根因
工具消息不是以 `type: "message"` 下发的，而是**搭在 `type: "tool_result"` 事件里**
一起给前端（`chat/agent.py` 里多个地方可以验证）。而前端的 `handleEvent`
只拿这个事件去更新"正在调用"的步骤条，**把 `event.message` 丢掉了**。
于是浏览器里的 `messages` 永远缺工具消息，"调用 + 结果"卡片显示不出返回内容 ——
靠回合结束后那一次全量重拉才补回来。

这也是为什么"去掉重拉"不能先于"接收工具消息"做。

### 怎么改的
1. `handleEvent` 的 `tool_result` 分支把 `event.message` 收进 `messages`（按 id 去重）。
2. `runStream` 的 `finally` 只保留 `loadConversations()` —— 列表里的标题/计数/成本会刷新，
   而消息本身已由 SSE 增量补齐。
3. 新增「↑ 加载更早的消息」按钮，配合 `before_seq`；
   加载后按新增内容的高度把视口挪回去，否则会被"新内容滚到底"拽回底部，等于白翻。

### 为什么这么改
- **为什么不新增一个轻量接口拉汇总**：消息已经在了，再拉一遍纯属浪费；
   SSE 是增量推送，重复拉取会和它产生竞态（比如把乐观插入的消息冲掉）。
- **为什么翻历史要补偿滚动位置**：用户往上翻是为了看上面，
  一翻就跳到底部会让这个功能没有意义。

## 4. Agent 链路去冗余查询（P1）

做了两件，**明确保留了一件**。

### 4.1 `_user_request` 提到循环外 ✅
同一个任务里 `user_request` 不会变，原来却在**每个 todo 步骤**都重新 `select(Task)` 查一次。
现在在 `_execute` 开头取一次，当参数传下去。

### 4.2 素材号改为内存聚合 ✅
`_artifacts(task_no)` 原来为了汇总产物文件，会把 `task_todos` **再全表查一遍**。
但 `_execute` 开头取 `rows` 快照时已经把 `artifact_nos` 读出来过一次了。
改成 `_artifact_refs(rows, run_artifacts)`：快照覆盖"之前就做完的步骤"，
本轮各步的 outcome 覆盖"这次新产出的"，两者合并就是全部。

### 4.3 `_metrics` 仍查库 —— 刻意保留 ❌
原计划也想改成内存累加，评估后决定不做：

任务级 token / 成本必须反映**库里的真实值**，要考虑恢复执行、失败重试这些路径。
快照里的值是**旧的**，本轮跑完会被**覆盖**而不是**累加** ——
想在内存里算对，必须逐分支判断"这一步的旧值要不要减掉"，漏一条就是重复计数或漏计。
**拿一条聚合 SQL 换正确性不划算**，所以保留。

同理，`_set_todo` 每次都新开短事务、按 `task_no` 重查 Task 也没动：
`store.py` 的注释说明这是"短事务 / 断连安全"的**刻意设计**
（执行器可能跨进程恢复，长事务会锁住任务行），合并事务收益不抵风险。

## 5. 补齐分页与真实 `total`（P2）

| 接口 | 原来 | 现在 |
|---|---|---|
| `/api/v1/kb` | 全表返回 | `Page[KBArticleOut]` 分页 |
| `/api/v1/memories` | 无上限 | `limit` 默认 200、上限 500 |
| `/api/v1/conversations` | `total = len(rows)` | **真实总数** + 支持 `offset` |
| `/api/v1/metrics/daily` | 无 limit | 不加（见下） |

### 一个真实的语义 bug
`conversations` 的 `total` 写的是 `len(rows)`，而 `rows` 最多只有 `limit`（默认 50）条 ——
**这个 total 永远等于本页条数**。后果有两个：
前端算不出页数；更重要的是**第 51 个会话用户永远看不到**。
现在改成 `store.count_conversations()` 的真实总数，并补了 `offset`。

这也是第 7 项「加载更多」按钮能做得出来的前提。

### 为什么 `metrics/daily` 不加 limit
它的结果条数已经被 `days` 的 `le=180` 天然限死（最多 180 行），
再加一个 `limit(365)` 是永远不会生效的无效代码。
真正的开销是"每次请求都重跑聚合"，这个问题已由第 1 项的缓存解决。

## 6. 补两个索引（P2）

- **`tickets(status, created_at)`**：工单列表是「按 `status` 过滤 + `created_at` 倒序」。
  已有的 `ix_tickets_status_priority` 第二列是 `priority`，覆盖不了这个排序，
  于是每次都要 filesort。补一个顺序对得上的。
- **`email_messages(gate_decision)`**：这个字段既被邮件列表用来精确过滤
  （含 `LIKE 'blocked%'`），又被 `email_gate_stats` 拿去 `GROUP BY`，两种用法都没有索引可走。

索引是纯性能改动，**不影响任何数据语义**，所以迁移的 downgrade 就是两个 `DROP INDEX`。
迁移文件：`backend/migrations/versions/20260920_1200_c1d2e3f4a5b6_query_indexes.py`（已应用到开发库）。

## 7. 前端渲染与分页（P2）

- **`visible` 包进 `useMemo`**：原来每次改变也会重新过滤一遍消息数组，现在按 `messages` 记忆化。
- **会话列表「加载更多」**：依赖第 5 项的真实 `total`，`offset` 取当前列表长度追加下一页。
  这里能用列表长度当 offset，是因为**列表里每一行都对应服务端的一行**，不存在"本地有、服务端没有"的项。

### 消息列表虚拟化：没做，理由
需要新增依赖，而消息行**高度不固定**（工具结果是 `<details>` 可展开的），
定高虚拟化得自己写动态测量。当前单次只取最近 100 条、更早的要手动翻，规模已经压住了。
**触发条件**：单场对话常态超过 ~300 个渲染行时再上，届时选支持动态测量的
`@tanstack/react-virtual`，而不是定高的 `react-window`。

## 8. 理顺 Redis 库用途（P3）

`cache.py` 约定的分工是 db1=网关限流/熔断、db2=业务缓存。
但网关的**幂等存储**属于网关状态，却落在 db2 上，结果是 **db1 闲置、db2 被网关占用**。
这在第 1 项做完之后尤其别扭：想清业务缓存，得小心别把幂等记录一起冲掉。

已把 `gateway/core.py` 的幂等存储改回 `DB_GATEWAY`，`DB_CACHE` 干净留给业务缓存。
影响：这是一次性的键迁移（旧的幂等 key 留在 db2 自然过期），功能不受影响。

## 不做清单（都有明确理由）

| 项 | 为什么不做 |
|---|---|
| `_metrics` 内存累加 | 必须反映库里真实值，含恢复/重试路径，改内存算有重复计数风险 |
| `_set_todo` 合并事务 | 破坏"短事务/断连安全"的刻意设计 |
| `metrics/daily` 加 limit | `days ≤ 180` 已天然限死，加了也不生效 |
| 消息列表虚拟化 | 需要新依赖 + 动态高度测量，当前规模还没到（触发条件见上） |
| `reporting.py` 收口 | **原判断有误，已撤销**：它是 openpyxl 样式封装，被 `tools/report.py` 用来生成 xlsx，和 dashboard 聚合不是一回事，没有重复逻辑 |

## 使用上要注意的一点

`/api/v1/summary`、`/products/categories` 等聚合接口现在**最多有 30 秒的数据延迟**
（`business_cache_ttl`，可调）。这是拿"实时精确"换"不用每次都跑聚合"的取舍。
如果某个场景必须实时，两种办法：调小 `FASHIONOPS_BUSINESS_CACHE_TTL`，
或在写路径上补一次 `invalidate_namespace("对应命名空间")`（参照 recorder 里的做法）。
