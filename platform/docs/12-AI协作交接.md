## 1. 一句话任务

**把任务的执行架构从「模型出 DAG → hub 按图路由 → 3 个专用节点」换成「一个 Agent + 显式 todo 列表」。**

用户原话（就是他交办这件事时说的）：

> 这一步很奇怪用户问完然后这个编排有什么用吗结果到哪里了最终这条也没有记录留存，
> 感觉就是有个任务编排告诉他用来哪里的代码很奇怪不能优化的话不好用就删了

### 他为什么这么说 —— 我查出来的事实（**别重新查一遍**）

任务 `T26091614214797C2`（"挑 5 款适合上新的秋季连衣裙"）的真实执行轨迹：

| seq | 节点 | 耗时 | tokens |
|---|---|---|---|
| 2 | `plan` | 20.1 s | 2003 |
| 5 | `selection` | 29.1 s | 2715 |
| 7 | `approval_gate` | — | 停在等人确认 |

计划本身是**对的**（`select_score_clothes` → `notify`，后者要审批），链路也跑通了。
但用户感觉"很奇怪"，因为下面 4 件事都是真的：

#### 问题 1：停在审批闸口的任务，界面上永远显示「0 次 / 0 tokens / ¥0.0000」← **真 bug**

`agents/recorder.py` 的 `mark_waiting_approval()` 只写 `status` 和 `approval_payload`，
**从不写 `llm_calls` / `total_tokens` / `total_cost`**。只有任务**跑到底**那条路径
（`runner._settle` → `recorder.finish(...)`）才会写这三个字段。

于是任何停在人工闸口的任务，明明已经烧掉 4718 tokens，界面上却是 0。
这就是用户截图里那行数字的来源。

> **新的 `task_todos` 设计已经针对这个坑做了防护**：计量按**每一步**记
> （`task_todos.llm_calls/total_tokens/total_cost`），任务级数字由步累加，
> 不再"只在最后写总数"。接手时**不要**退回"只在任务上记总数"。

#### 问题 2：模型自己加了一步用户没要的「发邮件」

用户的话里**没有一个字**提到邮件/通知。但计划第二步是 `notify`，
goal = "发送适合上新的秋季连衣裙邮件"，还标了 `approval_required=true`。

兜底模板 `default_plan_for()` 是按关键词判的（`发给/邮件/通知/告知/汇报`），
用户的话里一个都没有 → **这一步是模型自己加的，不是代码加的**。

后果：问一个只读问题 → 规划 20 秒 → 跑一步选品 → 停下来问"要不要发邮件"。
**这就是"这个编排有什么用"最直接的来源。**

#### 问题 3：界面上那行"规划理由"是自修复日志，不是理由

显示的是"合并了 selection Agent 的步骤，修正了重复使用的问题" ——
这是规划校验器发现模型重复用了 selection、触发修复重试后的**内部记录**，
被写进 `plan.reasoning` 直接展示给用户。它回答"我改了什么"，不是"为什么这样拆"。

#### 问题 4：`running` 没有超时，挂了就是永远

库里当时有一条 2026-09-08 的任务卡在 `running`（node=notify，5 次 LLM，
94485 tokens，**8 天**）。后端一重启，正在跑的任务就永远停在 `running`。

> 用户对这条的决定：**先手工收口，不写机制**。
> 我已经用 `TaskRecorder.finish()` 把它标成 `failed` 并保留了它的真实消耗
> （94485 tokens / ¥3.04），还写了事件说明原因。`running` 任务数现在是 0。
> **超时回收机制按用户的意思暂时不做** —— 但注意 §4 的新架构会从根上消掉这个问题。

### ☐ T4. 写「一个 Agent + todo」的执行循环

**做什么**：`agents/loop.py`（名字自定）。核心：

1. 调 `workplan.plan_todos()` → 落库到 `task_todos`（全是 `pending`）
2. 把 todo 列表放进系统提示，让 Agent 从第 1 步开始做
3. Agent 用工具做事，通过一个 `todo_update(seq, status, summary)` 工具**自己汇报进度**
4. 跑到需要审批的工具 → 见 T5
5. 全部做完 → 汇总写 `tasks.result`

**关键约束**：
- **只有一个 Agent**，不要按 todo 分派给不同的"节点"。
- 工具目录按当前 todo 的 `kind` 裁剪（选品那步不该看到发邮件的工具）。
- 每一步结束都要更新 `task_todos` 的计量字段（见 §1 问题 1）。

**参考**：`chat/agent.py`（753 行）里已经有一个成熟的工具循环实现
（`stream_turn` / `run_tool_loop` / 工具结果回喂 / `MAX_TOOL_STEPS`），
**先读它**，能复用就复用 —— 它踩过的坑包括：工具名回放要用
`gateway.registry.to_llm_name()` 转换（见 §7）。

**验收**：提交"挑 5 款适合上新的秋季连衣裙" →
只跑 1 步、**不出现审批闸口**、`task_todos` 里有 1 行且 `status=done`、
`tasks.llm_calls/total_tokens` 不是 0。

### ☐ T5. 审批：不阻塞线程

**这是替代 LangGraph `interrupt()` 的关键。** 现在靠 `interrupt()` 抛异常 +

## 5. 架构决策的详细理由

> 这一节解释 D5~D8"为什么这么定"，避免接手方"看起来可以简化"而改回去。

### 5.1 为什么 todo 是线性列表而不是 DAG

原来的 DAG 能表达分支和汇合，代价是：

- 图是**静态构建**的（一个 Agent 一个节点），所以规划校验里必须禁止
  `duplicate_agent` —— "同一个 Agent 干两件不同的事"表达不了。
- 有依赖就要做**传递阻断**（上游失败 → 下游全跳过，不能拿残缺输入接着算）。
  这段传播逻辑本身就是一类 bug 的来源（`planner.blocked_steps` 那一大段注释）。
- **最关键：表达力用不上。** 真实需求就是"选品 → 出报表 → 发邮件"一条线。

换成有序列表：第 n 步做完做第 n+1 步。少掉的是用不上的表达力，
换来的是"计划长什么样"和"现在跑到哪了"一眼看完 —— 这正是任务详情页要回答的两个问题。

### 5.2 为什么规划交代码，不交模型

原来让模型规划，实测两个问题：① 固定花 **20 秒 / 约 2000 tokens**（每个任务都要付，
哪怕只是问个库存）；② **它自己加用户没要的步骤**（§1 问题 2）。

改成代码判，代价是"认不出来的组合就不拆"。但这正是本项目的原则：
**判据放代码**（可审计、可回归、可解释）。认不出来时退化成单步任务，
而不是编一步出来。

### 5.3 为什么物理表名还是 `chat_approvals`

类名改成了 `Approval`（它不再只服务对话），但**表名没改**。理由是重命名买不到对应价值：

- `conversation_id` 上有外键。MySQL 里这个索引被外键占着，直接 `DROP INDEX`
  会报 **errno 1553**（`Cannot drop index ... needed in a foreign key constraint`）——
  得先造一个新索引顶上去才能删。
- SQLite 的 `batch_alter_table` 是**重建整表**，重建后索引名怎么落取决于它自己，
  最后"迁移过的库"和"新建的库"索引名会分叉，`alembic check` 会一直报。

为一个纯装饰性的重命名搞出一个高风险迁移不划算。真要改，
等下次有别的理由动这张表时一起做。

### 5.4 为什么审批要"结束本次运行"而不是阻塞

LangGraph 的 `interrupt()` 是**抛异常**中断的，靠 checkpointer 落盘，
人确认后用同一个 `thread_id` 重新 invoke。不用图之后没有 checkpointer 了。

如果改成"线程阻塞在那里等"，就回到了老问题：**后端一重启，等待中的任务就废了**。
所以改成"写库 + 结束运行"，等待状态全在数据库里，重启无感，
批准后重新发起一次运行即可。见 T5。

## 7. 踩过的坑（**动手前务必读完这节**）

### 7.1 工具 / 环境（Windows）

- **终端命令一定要短。** 我这次就被截断过一条长命令，PowerShell 卡在
  `Pattern[0]:` 参数提示上，只能杀掉终端重开。
  多语句命令的输出会被截断/错乱 → **拆成短命令，一次一件事**。
- **不要用 `Set-Content` / `Out-File` 改文本**（编码会坏）。用编辑工具。
- 中文输出要 `$env:PYTHONIOENCODING="utf-8"` + `$env:PYTHONUTF8="1"`；
  或者干脆让脚本把输出写进文件再读。
  > 注意：stdout 改成写文件后，终端会显示"Command produced no output"——
  > **不是失败**，去看那个文件。
- **不要在 PowerShell 里用 here-string 给 `python -c` 传多行源码**
  （`f"..."` 的 `f` 会被吃掉、`@router.get` 会被当 splatting）。
  **写临时 `.py` 文件再执行**。
- 临时脚本放 `platform/scripts/_*.py`，**提交前必须删掉**。
- 提交信息用临时文件 + `git commit -F`（PowerShell 会把多行 `-m` 弄坏）。
- `platform/data/eval/ticket_labels.json` 在 gitignore 的 `data/` 下但**有意被跟踪**，
  改它要 `git add -f`。
- **绝对不要把密钥经模型转发**（不进 `vscode_askQuestions`、不进命令行）。
  演示账号 `demo/FashionOps@2026` 是有意的例外（本地演示、写在 README 里）。

### 7.2 数据库 / 迁移（全是"只在 MySQL 上炸"型）

- **MySQL 的 DDL 不支持事务回滚。** 迁移失败会留下**半截状态**：
  前面的 DDL 已生效、`alembic_version` 还没更新 →
  "版本号说没事、实际库是坏的"。**迁移失败后必须直接查库确认真实状态**，
  别信版本号。
- **downgrade 里不要 `drop_index` 之后再 `drop_table` 同一张表。**
  MySQL 的外键会复用同名索引，单独 DROP 报 **errno 1553**；
  而 `DROP TABLE` 本来就会带走索引和外键。
  `tests/test_migrations.py` 里有静态检查器拦这个（我这次刚修过它的误报，见 §3.3）。
- **`alembic.ini` 必须是纯 ASCII。** Alembic 用 `encoding="locale"` 读它，
  中文 Windows 上是 GBK → 一个中文就 `UnicodeDecodeError`，
  **连 `--help` 都跑不了**。`PYTHONUTF8=1` 救不了（走的是 `locale.getencoding()`）。
- **MySQL 是 REPEATABLE READ。** 路由的 session 在鉴权时已经读过数据 →
  快照冻结 → **看不到另一个事务刚提交的行**。所以"构造好的 dict 直接返回，
  不要回库再查一遍"。这个坑在 SQLite 上**永远不复现**。

### 7.3 FastAPI / 后端

- **`get_db` 的 commit 跑在响应发出之后**（FastAPI 0.141.1 把依赖的
  `AsyncExitStack` 放在中间件里的 `response(scope, receive, send)` **之后**退出）。
  实测 20/20 次登录都看不到刚插入的 refresh_token 行（滞后 4~29 ms）。
  **这条还没修**，记为 P0-5，见 §8。
  现在只靠"时序运气"在工作 —— 涉及"先落库再返回"的逻辑要格外小心。
- **SSE 的事件名不要用 `error`**（`EventSource` 自带 `error` 事件），
  也不要在 SSE 的 `event:` 字段里重复 `data.event_type` —— 同一份信息存两处，
  后端新增事件类型时前端会**静默漏掉**。
- **接口返回的 id 必须立即可查。** 别把"插库"这件事交给后台线程 ——
  前端拿到 id 立刻 GET 会 404（这个坑真踩过）。
- **`error_message` 有值 ≠ 任务失败**（邮件被闸门拦下也会有值）。
  展示层要按**终态**挑措辞，不能只看"字段有没有值"。

### 7.4 对话 Agent（`chat/`）—— 你大概率要参考它

- **工具名回放必须转换。** 库里存的是 `erp.query_inventory`，
  而声明的 function 名是 `erp__query_inventory`。直接回放的话模型会
  **学会"工具名就是长这样的、可以写在正文里"**，于是它把工具调用写成**纯文本**。
  只在**第 2 轮起**才触发，看起来特别像"模型不稳定"。
  修法是 `to_llm_messages` 里过一遍 `gateway.registry.to_llm_name()`。
- **给 glm-4-flash 的输出格式约束要用"填好值的完整样例"**，
  不要给 JSON Schema —— 小模型会**把 Schema 原样回声**回来，
  延迟从 7 s 涨到 30 s。手写一个填好值的样例 + 人话写的字段约束，
  再加一道运行期自检（样例的键必须和 Pydantic 字段集合一致）。
- **平票不能按字典顺序取胜。** `classify_intent` 初版"命中数更大的胜出"，
  平票时赢家取决于 dict 顺序 —— 实测错了 2 条。改成**平票返回空**，交给下一层判。
- **`mark_waiting_approval` 那个坑**（§1 问题 1）虽然不是对话侧的，
  但同一个教训：**旁路写库失败会被 `_safe` 吞掉，只留一行 warning**。
  所以 `TaskRecorder` 有 `write_failures` 计数器 ——
  **任何 fail-safe 都必须配一个可观测的计数**，否则它迟早掩护一个真 bug。
