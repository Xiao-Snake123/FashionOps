# 优化待办清单（性能 / 架构）

> 目标：在不改动功能的前提下，梳理后端、前端、数据库里可做的性能与架构优化点，
> 形成一份可执行的待办清单。
>
> 范围：后端 `backend/fashionops` + 前端 `frontend/src`。
> 排查方式：静态只读扫描（含列表接口分页、`N+1`、序列化、缓存命中、Agent 链路、索引）。
> 首次排查：2026-09-20；**第一轮实施：2026-09-20（见文末「实施记录」）**。
>
> 勾选约定：`- [x]` 已完成，`- [ ]` 待做，`- [~]` 已评估、决定不做（附理由）。

## 1. P0 · 后端：真正启用 Redis 业务缓存（投入产出最高）

- [x] **让 `DB_CACHE`（db=2，定义为"业务缓存：列表页、聚合结果"）真正被读接口使用**
  - 原状：`cache.py:32` 定义了 `DB_CACHE`，但全局只有 `gateway/core.py` 的**幂等存储**
    在用 `get_redis(DB_CACHE)`，没有任何列表/聚合接口命中它。
  - 已做：`cache.py` 新增 `business_cache_key` / `read_cached_json` /
    `write_cached_json` / `invalidate_namespace`；`config.py` 新增
    `business_cache_enabled`（总开关）与 `business_cache_ttl`（默认 30s）。
    已接入：`/api/v1/summary`、`/api/v1/metrics/daily`、`/api/v1/products/categories`、
    `/api/v1/inventory/low-stock`、`/api/v1/kb`。
  - ⚠ **测试里必须关**：`tests/conftest.py` 加了 autouse 夹具 `business_cache_off`。
    不关会**跨用例串数据** —— 每个用例用自己那份临时 SQLite 库，而 Redis 是共享的，
    用例 A 的缓存会被用例 B 命中，且只在 Redis 真的在跑时才复现。
  - 失效：`invalidate_namespace()` 已接进 `agents/recorder.py` 的
    `start` / `update_progress` / `finish` —— 任务状态一变就让 `summary` 失效，
    不必干等 30 秒 TTL（否则会出现"刚点了批准，运行中的数量还是 0"的滞后）。

## 2. P1 · 后端：会话详情历史加 `limit` + 滚动加载

## 3. P1 · 前端：去掉每回合全量重拉会话历史

- [x] **`Chat.tsx` 每次发完消息都全量重拉整个会话历史**
  - 已做：`runStream` 的 `finally` 里只保留 `loadConversations()`（刷新标题/计数/成本），

  - 配套：新增「↑ 加载更早的消息」按钮（`before_seq` + 视口位置补偿，翻完不跳回底部）。

## 4. P1 · 后端：Agent 链路去掉冗余查询

- [x] **`_artifacts` 重复查询 `task_todos`**
  - 已做：改成 `_artifact_refs(rows, run_artifacts)` —— 直接用开跑前取回的
    `rows` 快照里的 `artifact_nos`，加上本轮各步 outcome 新产出的，不再单独查库。

- [~] **`_metrics` 在结束时再查一次 `task_todos`：评估后保留**
  - 理由：任务级 token/成本必须反映**库里的真实值**（含恢复执行、失败重试等路径）。
    改成内存累加需要把 `rows` 快照的旧值替换成本轮新值，一旦漏掉某条分支就会
    **重复计数或漏计**。这里一条聚合 SQL 换正确性不划算，保持原样。

- [x] **`_user_request(task_no)` 每个 todo 步骤都重新查库**
  - 已做：`_execute` 开头取一次，作为参数下传。

- [~] **每个 `_set_todo` 都新建 session 并按 `task_no` 重查 Task：评估后保留**
  - 理由：`store.py` 的注释明确写了这是"短事务 / 断连安全"的**刻意设计**
    （执行器可能跨进程恢复，长事务会锁住任务行）。合并事务能省一点往返，
    但会破坏这个前提，收益不抵风险。

## 5. P2 · 后端：补齐分页与真实 `total`

- [x] **`GET /api/v1/kb` 无分页/无 limit，全表返回**
  - 已做：改成 `Page[KBArticleOut]`（复用 `_paginate`），缓存 key 带上 `page`/`page_size`。

- [~] **`GET /api/v1/metrics/daily` 无 limit：评估后不加**
  - 理由：结果条数已经被 `days` 的 `le=180` 天然限死（最多 180 行），
    再加 `limit(365)` 是无效代码。真正的开销是"每次都重跑聚合"，
    已由条目 1 的缓存解决。

- [x] **`GET /api/v1/memories` 无 limit**
  - 已做：`limit` 默认 200、上限 500。

- [x] **`GET /api/v1/conversations` 只有 `limit`、无真正分页，`total` 语义错误**
  - 已做：新增 `offset` 参数，`total` 改为 `store.count_conversations()` 的**真实总数**
    （原来是 `len(rows)`，最多 50，第 51 个会话永远看不到）。

## 7. P2 · 前端：列表渲染与分页

- [x] **`visible = messages.filter(...)` 未 `useMemo`**
  - 已做：包进 `useMemo(() => ..., [messages])`。

- [x] **会话列表仅 `limit:50`、无分页 UI**
  - 已做：侧栏底部新增「加载更多（还有 N 个）」，`offset` 取当前列表长度追加下一页。
    依赖后端条目 5 的真实 `total` —— 以前 total 恒等于 50，这个按钮根本没法做。

- [~] **消息列表虚拟化：评估后暂不做**
  - 理由：需要新增 `react-window` 依赖，而消息行高度**不固定**（工具结果是 `<details>`
    可展开的），定高虚拟化要写动态测量，复杂度和收益不匹配。
  - 当前的规模已被压住：单次详情只取最近 100 条，更早的要手动翻。
  - **触发条件**：单场对话常态超过 ~300 个渲染行时再上虚拟化，届时优先选
    支持动态测量的 `@tanstack/react-virtual` 而不是定高的 `react-window`。

## 已排查、无明显问题的点（避免重复劳动）

- **分页正常**：`list_products` / `list_tickets` / `list_campaigns` / `list_assets` /
  `list_emails` 均有 `_paginate` 或显式 limit；`low_stock` 有 `.limit(200)`。
- **序列化未引发 N+1**：列表 schema（`ProductOut`/`TicketOut`/`EmailOut`/`TaskOut` 等）
  均不含关系字段，`Product.skus` 虽 `lazy="selectin"` 但从未被 list schema 触发。
- **Agent 历史管理良好**：`chat/agent.py:_drive` 用 `memory.context_limit()` 限制历史、
  开跑前预取长记忆块、仅超窗时刷新摘要。
- **向量检索有界**：`tools/kb.py` 有 `MAX_TOP_K=8` + 预过滤；
  `chat/longterm.py` 按设计"每轮全量注入最近 N 条（默认 20）"，注释已说明取舍。
- **前端无轮询**：任务/对话均走 SSE；各页面用 `Promise.all` 并行拉取。
- **核心索引到位**：`ix_chat_conv_user_updated`、`ix_chat_msg_conv_seq`、
  `ix_agent_memory_user_updated`、`ix_products_*`、`ix_kb_category_active`、
  `ix_bi_metric_date`、`ix_orders_*`、`ix_task_events_task_seq`、`ix_audit_*` 等。
